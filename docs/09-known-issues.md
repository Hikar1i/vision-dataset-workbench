## 状态机已知偏差

- 缺失视频文件只会把 `DOWNLOADED`、`READY_FOR_SAMPLING`、`SAMPLED` 修复为 `ERROR`，不会处理已分组或已过滤状态。
- 配置加载只更新精确等于 `SAMPLED` 的视频，跳过仍可导出的分组/过滤状态。
- 分组逻辑的默认分支可能把其他状态重置成 `SAMPLED`。
- 已抽帧视频不能通过正常状态守卫重新抽帧。
- 下载和抽帧的瞬时 UI 状态与持久业务状态没有可靠任务记录连接。

新状态机实现前应把这些场景写成回归测试，明确保留、修正或通过迁移兼容。

## 算法与性能限制

- 前端“按标注批量启停”逐帧请求标注，复杂度约 O(视频数 × 帧数)。
- 前端分组是排序后的蛇形分配，不保证各组总帧数最均衡。
- 超过 1000 个启用帧的视频强制进入训练集，可能使验证集比例明显偏离配置。
- 抽帧进度通过每 0.5 秒扫描输出目录计算，大目录成本会增长。
- 本地视频 ID 需要读取全文件 MD5，并截断为 11 个字符。

这些算法不是全部都必须替换；实现前应把当前行为固化为测试，再根据真实数据基准决定。

## 批量抽帧页面卡顿

遗留代码没有为抽帧设置全屏遮罩，卡顿更可能由以下已确认机制叠加造成：

- 前端同时触发 3 个抽帧请求。
- 后端每个请求创建 daemon thread，并启动未限制线程数的 FFmpeg。
- 多个 FFmpeg 同时竞争 CPU 与磁盘 I/O。
- FFmpeg stderr 写入 PIPE，但运行期间不持续读取，长任务存在管道写满风险。
- 每个任务每 0.5 秒扫描帧目录并发送进度。
- 前端每次进度都更新大型响应式表格并同步写 localStorage。

已批准的新系统方案：

- API 只创建任务并立即返回 `202`。
- 独立 Worker 执行任务，抽帧默认全局并发 2、每用户 1。
- 限制每个 FFmpeg 的线程数，持续消费 stdout/stderr。
- 使用 `-progress pipe:1`，进度最多每秒持久化和推送一次。
- 前端只更新相关视频行和任务抽屉，不写进度 localStorage、不显示全屏蒙版。
- Worker 重启、任务取消和重复提交进入自动化测试。
