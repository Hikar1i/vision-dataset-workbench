# 已知问题

状态：应用基础、视频导入、采样、抽帧、帧筛选、项目标签和 GPU 能力检测已实现；下表同时记录当前限制、遗留风险和已批准方案。

## 当前项目限制

- 当前已能初始化、登录、管理用户/项目/标签、导入本地或远程视频、配置/执行采样、筛选帧、查看任务并播放/下载原始视频和帧图片；标注记录、模型推理和导出尚未实现，项目删除、归档和所有权转移也未提供。
- systemd、Windows 启动器和 Docker Compose 尚未实现；当前 Worker 需单独手工启动。
- GPU 能力只在 API 进程启动时检测并缓存，不反映动态显存占用，也未实现设备选择、模型文件就绪判断和任务调度；环境变化后需重启 API。
- 前端全量导入 Element Plus，当前生产主 JavaScript chunk 约 1,062 kB；业务页面增加后应按测量结果拆包或按需导入。
- 任务抽屉当前打开时每秒轮询，不提供 SSE；当前任务量和并发目标较低时可接受，如实测产生明显请求或交互压力再引入事件推送。
- 当前运行拓扑只支持每工作区一个调度 Worker。租约能恢复进程退出遗留的 running 任务，但未实现跨服务器 Worker 协调或网络文件系统支持。
- 当前同源校验不信任代理头；在 TLS 终止反向代理后直接使用前，必须补充明确的代理配置与测试，否则 HTTPS origin 可能与应用观察到的 scheme 不一致。
- FastAPI/Starlette 测试客户端当前产生上游弃用警告，不影响测试结果；依赖升级时应移除该警告。
- owner/editor/viewer 授权规则已通过自动化和实际进程冒烟验证，但常规并发目标尚未基准验证；恢复时间与恢复点目标仍为 `Unknown`。
- `.ai-local/` 中的研究与参考材料是本地内容，不应被运行时或 CI 依赖。

## 状态机已知偏差

- 缺失视频文件只会把 `DOWNLOADED`、`READY_FOR_SAMPLING`、`SAMPLED` 修复为 `ERROR`，不会处理已分组或已过滤状态。
- 配置加载只更新精确等于 `SAMPLED` 的视频，跳过仍可导出的分组/过滤状态。
- 分组逻辑的默认分支可能把其他状态重置成 `SAMPLED`。
- 已抽帧视频不能通过正常状态守卫重新抽帧。
- 下载和抽帧的瞬时 UI 状态与持久业务状态没有可靠任务记录连接。

新状态机实现前应把这些场景写成回归测试，明确保留、修正或通过迁移兼容。

## 算法与性能限制

- 前端“按标注批量启停”逐帧请求标注，复杂度约 O(视频数 × 帧数)。
- 前端分组是排序后的蛇形分配，不保证各组总帧数最均衡。
- 超过 1000 个启用帧的视频强制进入训练集，可能使验证集比例明显偏离配置。
- 抽帧进度通过每 0.5 秒扫描输出目录计算，大目录成本会增长。
- 本地视频 ID 需要读取全文件 MD5，并截断为 11 个字符。

这些算法不是全部都必须替换；实现前应把当前行为固化为测试，再根据真实数据基准决定。

## 批量抽帧页面卡顿

遗留代码没有为抽帧设置全屏遮罩，卡顿更可能由以下已确认机制叠加造成：

- 前端同时触发 3 个抽帧请求。
- 后端每个请求创建 daemon thread，并启动未限制线程数的 FFmpeg。
- 多个 FFmpeg 同时竞争 CPU 与磁盘 I/O。
- FFmpeg stderr 写入 PIPE，但运行期间不持续读取，长任务存在管道写满风险。
- 每个任务每 0.5 秒扫描帧目录并发送进度。
- 前端每次进度都更新大型响应式表格并同步写 localStorage。

新系统已按以下方式处理：

- API 只创建任务并立即返回 `202`。
- 独立 Worker 执行任务，抽帧默认全局并发 2、每用户 1。
- 限制每个 FFmpeg 的线程数，持续消费 stdout/stderr。
- 使用 `-progress pipe:1`，进度最多每秒持久化和推送一次。
- 前端只更新相关视频行和任务抽屉，不写进度 localStorage、不显示全屏蒙版。
- Worker 重启、任务取消、并发限制和重采样保护进入自动化测试；真实 FFmpeg 冒烟确认 API 在抽帧期间独立运行。

## 延期功能风险

图片分支依赖遗留 Python 去重脚本、外部模型与同步文件移动。模型权重来源、许可、资源需求和准确率均为 `Unknown`。在视频主链路重构完成前只保留需求与证据，不直接合并实现。
