- 训练子进程、事件、指标、双 GPU 并行和发布已由确定性假训练集成测试覆盖，并已用真实 YOLO11n 在 GPU 1 完成 2 epoch 冒烟；尚未用长时训练执行 retry/resume/derive/extend 全操作矩阵。模型转换、在线推理和评估页面已在 Chrome 以 1920×1080、2560×1440 完成人工视觉验收，但项目仍未配置自动化像素级视觉回归。

## 遗留状态机已知偏差

- 缺失视频文件只会把 `DOWNLOADED`、`READY_FOR_SAMPLING`、`SAMPLED` 修复为 `ERROR`，不会处理已分组或已过滤状态。
- 配置加载只更新精确等于 `SAMPLED` 的视频，跳过仍可导出的分组/过滤状态。
- 分组逻辑的默认分支可能把其他状态重置成 `SAMPLED`。
- 遗留系统的已抽帧视频不能通过正常状态守卫重新抽帧；当前系统已改为普通/强风险分级确认，并由后端实时守卫覆盖操作。
- 下载和抽帧的瞬时 UI 状态与持久业务状态没有可靠任务记录连接。

新状态机实现前应把这些场景写成回归测试，明确保留、修正或通过迁移兼容。

## 算法与性能限制

- 遗留前端“按标注批量启停”曾逐帧请求标注；当前实现已改为单次项目批量 API，服务端按数据库集合查询和事务更新处理。
- 前端分组是排序后的蛇形分配，不保证各组总帧数最均衡。
- 超过 1000 个启用帧的视频强制进入训练集，可能使验证集比例明显偏离配置。
- 抽帧进度通过每 0.5 秒扫描输出目录计算，大目录成本会增长。
- 本地视频 ID 需要读取全文件 MD5，并截断为 11 个字符。

这些算法不是全部都必须替换；实现前应把当前行为固化为测试，再根据真实数据基准决定。

## 批量抽帧页面卡顿

遗留代码没有为抽帧设置全屏遮罩，卡顿更可能由以下已确认机制叠加造成：

- 前端同时触发 3 个抽帧请求。
- 后端每个请求创建 daemon thread，并启动未限制线程数的 FFmpeg。
- 多个 FFmpeg 同时竞争 CPU 与磁盘 I/O。
- FFmpeg stderr 写入 PIPE，但运行期间不持续读取，长任务存在管道写满风险。
- 每个任务每 0.5 秒扫描帧目录并发送进度。
- 前端每次进度都更新大型响应式表格并同步写 localStorage。

新系统已按以下方式处理：

- API 只创建任务并立即返回 `202`。
- 独立 Worker 执行任务，抽帧默认全局并发 2、每用户 1。
- 限制每个 FFmpeg 的线程数，持续消费 stdout/stderr。
- 使用 `-progress pipe:1`，进度最多每秒持久化和推送一次。
- 前端只更新相关视频行和任务抽屉，不写进度 localStorage、不显示全屏蒙版。
- Worker 重启、任务取消、并发限制和重采样保护进入自动化测试；真实 FFmpeg 冒烟确认 API 在抽帧期间独立运行。

## 图像项目当前限制

- 新导入/标注/导出/训练快捷入口的隔离迁移、后端与前端回归已通过；独立 reviewer 的源码问题已修复复查。2026-10-26 已使用实际 Chrome 连接隔离应用，本轮双分辨率独立实机验收通过（UI/UX REVIEW PASSED）；未对真实项目执行停用重复图或删除。
- 图片 reflink→hardlink→copy；删除源路径安全，hardlink 原地改写共享 inode。导出按冻结 hash 检查变更，但发布后的外部原地改写仍可能影响受管图和快照，应保持来源不变或使用支持 reflink 的文件系统。
- 完全重复图片只在单次新快照内避免跨 train/val；增强同源图及多个既有快照之间的重叠未识别。目录内正负样本分别分层；不足两张无法保证两侧覆盖，不可拆重复组/固定角色也可能偏离比例，页面展示目标、实际和原因。跨目录重复组使用确定性局部优化，不承诺全局最优；新导入按SHA-256项目级去重，不覆盖旧标注；历史重复仍可显式一键停用，覆盖当前项目所有启用图片，确认弹窗说明范围。
- 只支持矩形 Detect、单页图像及正常 EXIF 方向；JSON/其他附件不叠加标注。大目录预检同步读取、解码和哈希，尚无实测规模上限，孤儿 TXT 警告较多时预检响应可能较大。
- Worker 每次领取使用独立 attempt staging，正常完成会清理；进程崩溃残留可能留在 tmp，清理须先停止 Worker 并核对活动任务，当前无自动垃圾回收。

- 测试集评估准备 YAML 原先只有 val，触发 Ultralytics 必填 train 校验；现补齐 train/val 声明且只执行 val。后台修复需 Worker 重载；旧失败记录需重新创建评估。

## 容器与转换产物兼容（2026-10-26）

- 首次初始化后未接线的模型推理/评估/产物服务已补齐；不再要求初始化后重启 API 才能使用。
- Ultralytics TensorRT 文件带长度和 JSON 元数据头；校验器现剥离合法头后反序列化引擎，保留原文件，同时兼容原始 TensorRT plan。真实转换与推理已通过。
- 固定尺寸 ONNX/engine 不能按默认 640 评估；评估现读取导出尺寸，并在类别元数据加载前指定租用 GPU。修复需重启 Worker，历史失败任务需重新创建。
- CPU 没有 TensorRT 时不再错误地把既有引擎判为环境失效；CPU 仍禁止执行，GPU 版继续检查源哈希和构建环境。
- 能力接口失败现按不可执行处理，同时保留成功读取的模型、下载和历史页面；提示刷新重试。
- Docker Desktop 的 macOS AMD 和 Windows Intel 集显按 CPU 模式运行；GPU override 只面向受支持的 NVIDIA 设备。驱动/容器运行时前提见[部署](07-deployment.md)。

前端品牌及浏览器事件/偏好键统一使用 VDW/vdw；升级后旧浏览器的侧栏折叠、标注标签沿用和通知已读等本地偏好会恢复默认，服务端账号、项目及标注数据不受影响。

CPU 版训练详情目前仍可能显示可点击的“开始训练”，不表示支持训练；实际执行由后端能力校验拒绝。本轮仅调整权限页入口，未统一此既有按钮的能力禁用展示。

同一 Docker 归档在本轮 Intel macOS Docker Desktop 加载后的 `image inspect .Id` 与 Linux/Windows 不同；归档 SHA256、RootFS层列表和镜像配置的哈希实际一致。跨这些镜像存储实现核对发布内容时，应同时验证归档和层/配置摘要，不能仅凭本地显示ID不同判断加载了旧版。

基础镜像可拉取，但构建容器 apt 访问 Debian 官方源超时：后续“找不到ffmpeg/libgl”等可能由索引下载失败引起。使用项目 `VDW_DEBIAN_MIRROR` 或构建代理，保留签名校验；见[构建网络排查](07-deployment.md#构建容器无法访问-debian-源)。
